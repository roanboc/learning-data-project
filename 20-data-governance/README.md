# 20 · Data governance

What data governance defines that isn't the data team's code: what words mean, who owns what, the
governance part of the architecture map, the data products and their contracts, each agent's mandate,
the information assets, the matrices and the metrics. At a real organisation each of these usually
lives in a tool of its own, or a whole suite: the glossary in a catalogue, the owners in a directory,
the map in an architecture tool, products and contracts in a product catalogue. A small organisation
may have none of them, and no governance team either: then these files are the least worth writing
down, and they are enough. Here they are text, in one folder, so people and agents can read them all.

| Folder | What | Written by | Standard |
|---|---|---|---|
| `1-glossary/` | The business glossary, `business-glossary.yml`: what the university's words mean, each with its owner; and the short forms the project can't avoid | Data governance; each term's owner decides it | |
| `2-owners/` | Who each owner is, and how the impact check reaches them (owners decide meaning in the glossary; they don't review pull requests) | Data governance, with the data architect | |
| `3-architecture-map/` | The governance part of Noor's map: capabilities, services, roles, steps, artifacts and where they live. It refines the enterprise architecture, `../10-enterprise-architecture/` | The data architect | ArchiMate's elements |
| `4-data-products/` | Each data product: owner, purpose, outputs, service levels, support | Each product's owner | |
| `5-data-contracts/` | The enterprise contract of each canonical table (a public model). Only canonical tables have one. The data team's other contracts are agreed team to team and need no agreement from data governance | Data governance's information architect, first; the data team builds the model to it | Open Data Contract Standard 3.1.0 |
| `6-product-descriptors/` | Each product, in the open standard | Generated by the data project's `scripts/generate/products.py` | Open Data Product Standard 1.0.0 |
| `7-standards/` | The standards' schemas, that the files are checked against | Copied from the standards | |
| `8-mandates/` | Each agent's mandate: the one kind of task it may do alone, and where, and what holds each line | Each agent's owner, approved by a second person | |
| `9-information-assets/` | Each information asset the questions need: owner, steward, level, personal data, where it is first recorded, its shared table, contract and products. Each one refines a data object on the enterprise architecture's map | Data governance; each owner confirms their rows | |
| `10-matrices/` | Which system records each asset, which products serve it; and who does what, on the map (`3-architecture-map/6-views/responsibilities.md`) | Generated by `scripts/check.py` | |
| `11-metrics/` | Each measure, defined once, with its owner | Each measure's owner | Apache Ossie 0.1.1 |
| `scripts/` | `check.py`: checks the assets and the metrics, and writes the matrices | | |

The folders are numbered in the order to read them. Files are named after what they hold, never by a code.

**Links point one way.** Governance cites the enterprise architecture (`UNI.DOBJ2.1`, a data object on its
map) and never the data project. The data project reads these files and checks itself against them:
`scripts/generate/products.py`, `scripts/check/architecture_map.py`, `scripts/check/mandates.py` and
`scripts/check/from_governance.py`, in `../30-data-project/`. What stays with the models, because dbt reads
it: each model's owner, columns' classes and tests, and the conceptual models and decision logs.

```bash
python scripts/check.py           # check the assets and the metrics, and write 10-matrices/
python scripts/check.py --check   # the same, failing if a matrix is out of date (CI)
```
